Platform handover

Deployment notes for the technical team or buyer. This page is documentation only; this single HTML prototype does not contain a production backend or process payments.

1. Environment variables

Configure these on the backend host's secret/environment settings. Never put secret values in this HTML file, browser JavaScript, source control, or public documentation.

NODE_ENV=production
PORT=3000
PUBLIC_APP_URL=https://your-domain.example
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DBNAME
SESSION_SECRET=GENERATE_A_LONG_RANDOM_SECRET
ALLOWED_ORIGINS=https://your-domain.example
LOG_LEVEL=info

# Payment provider — use only after the provider approves the gambling business
PAYSTACK_PUBLIC_KEY=pk_live_REPLACE_IN_SECRET_SETTINGS
PAYSTACK_SECRET_KEY=sk_live_REPLACE_IN_SECRET_SETTINGS
PAYSTACK_WEBHOOK_SECRET=SET_FROM_PROVIDER_CONFIGURATION
PAYMENT_CURRENCY=NGN
PAYMENT_CALLBACK_URL=https://your-domain.example/api/payments/callback

# Optional, if supported by chosen provider
PAYMENT_PROVIDER=paystack
PAYMENT_MODE=test

Variable names are an integration checklist, not a claim that the current HTML supports them. Confirm exact names and callback formats against the chosen backend and provider SDK. Use test credentials first; do not paste credentials into this page.

2. Payment-provider credentials & setup
  1. Create a merchant account with a provider that has explicitly approved this casino use case.
  2. Obtain test keys and configure them as backend secrets, not frontend variables.
  3. Configure the provider's webhook URL and verify webhook signatures server-side.
  4. Verify each payment with the provider server-to-server before crediting a wallet. Make processing idempotent so duplicate callbacks cannot credit twice.
  5. Store immutable transaction references and reconcile provider settlements against the ledger.
  6. Keep live mode disabled until test cases, provider approval, and operational sign-off are complete.
3. Deployment steps
  1. Build and deploy a backend service and PostgreSQL database; this standalone HTML file alone is not a full-stack casino.
  2. Serve the site over HTTPS using a domain you control.
  3. Set production environment variables in the hosting provider's secret manager.
  4. Run reviewed database migrations and configure automated encrypted backups and a tested restore process.
  5. Configure allowed origins, secure cookies, rate limits, monitoring, error reporting, and log redaction.
  6. Deploy to staging first; run payment, withdrawal, security, and recovery tests before production release.
  7. Document rollback steps, incident contacts, and provider support details for the buyer.
4. Initial admin setup
  1. Create the first administrator using a protected backend/CLI bootstrap command—not a public registration form or hard-coded password.
  2. Require a unique password and multi-factor authentication where available.
  3. Use role-based permissions and least privilege; separate support, finance, and system-administrator roles.
  4. Record admin actions in an append-only audit log and alert on sensitive changes.
  5. Test account recovery, admin offboarding, and emergency credential rotation.
  6. Do not use default credentials or expose admin endpoints without authentication and access controls.
5. Remaining production checks
  • Confirm applicable licences, market/jurisdiction restrictions, age and identity checks, AML/fraud controls, privacy notices, retention rules, and responsible-gambling tools with qualified advisers.
  • Obtain written provider approval for real-money gambling and confirm permitted deposit, payout, card, bank-transfer, or USSD methods.
  • Implement and test secure authentication, password hashing, session management, CSRF protection, rate limiting, and account lockout controls.
  • Implement a transactional wallet ledger; never trust client-supplied balances or credit funds from an unverified redirect.
  • Implement withdrawal review, account-name checks where supported, limits, fraud review, and payout reconciliation.
  • Integrate licensed/authorized game providers; confirm game certification, settlement callbacks, and round-level auditability.
  • Run dependency, vulnerability, penetration, load, backup-restore, and disaster-recovery tests.
  • Test deposits, failures, pending payments, refunds, duplicate webhooks, withdrawals, chargebacks, and reconciliation in staging.
  • Review all marketing claims, bonus terms, privacy policy, terms of service, and customer-support escalation processes.
  • Ensure no demo game, demo balance, or prototype message is mistaken for live-money functionality.
